## Scope

This patch release carries the post-1.0.0 fixes and release-readiness work.

- **Added/deleted-file anchor fix.** The shipped 1.0.0 runtime dropped every
  finding on an added or deleted file (and on any file ordered after one in the
  diff) on GitHub, because the prepared diff's `--- /dev/null` sentinel failed
  anchor-scan path validation; consensus then exited 3 and `post`/`gate` never ran.
  Anchor finalization now maps the added/deleted sides, so such findings are
  accepted. This closes the defect knowingly shipped in 1.0.0.
- **`render-body.v3` posted output.** Free-text and path-shaped model values render
  as literal data, malformed suggestions stay visible as data, and fragment-aware
  truncation keeps spans atomic, blocks closed, and trusted footers/markers intact.
  Prose now wraps instead of scrolling: bodies, evidence, and critique rationale
  render as one code span per line rather than a `text` fenced block, while
  suggestions keep the fenced block because they are code. Every model-authored
  value still renders inside a `code` or `pre` element, which is also the boundary
  keeping model text away from both platforms' post-render autolink, mention, and
  issue-reference filters. Consensus artifacts remain `consensus.v1`.
- **Reviewer model and effort defaults.** Model IDs in `review.yaml` must fully
  match the supported grammar; a malformed value, including a trailing newline, is
  rejected with `model_error` before the reviewer CLI is invoked. The Cursor
  permission smoke now requires an explicit exact model and rejects the discovery
  placeholder `auto` before invoking Docker.
- **Release-state tooling.** Prose claims about release state are now bound to
  `release-inputs.status` and enforced in `make quality`; live evidence moved to
  `docs/evidence/`; `scripts/scan_evidence_leaks.py` replaces ad-hoc credential
  greps.

## Migration

The posted-body format is `render-body.v3`. Existing bot-authored inline threads
receive a **one-time body update** on the next review run; issue IDs, state records,
and marker grammar are unchanged. Deployments tracking `main` before this change see
one further refresh, because the prose format changed within v3.

## Carried known limitations

Unchanged from 1.0.0 and not softened by this release: there is **no in-pipeline
trusted-image or trusted-composition enforcement** — a hostile consumer
`.gitlab-ci.yml` can substitute the pinned images, and containment comes from
credential withholding plus the out-of-band trust auditor. Network egress is
unenforced at the container/runner boundary. "Credential isolated" is claimable only
in the recorded sense — protected credentials withheld from an unprotected-ref MR in
the hardened child topology — and not as a product-wide property. GitLab forks are
untested. Cursor remains disabled pending the SPEC-21 enablement queue.

Cursor remains disabled for this release. Before enabling it, complete the
SPEC-21 checklist's explicit ask-mode decision and, if the chosen contract
requires Cursor-backed blocking findings, its blocking fixture and required-check
verification.

## Tagging

The external manifest binds `release_commit` and re-derives the `R..P` diff, so the
tag must point at a commit that satisfies it.

- **Do not squash-merge the release pull request.** A squash rewrites `P` into a new
  commit and drops it from `main`'s history, which invalidates the manifest.
- Either tag `v1.0.1` on `P` exactly, or rebuild and re-validate the manifest against
  the merge commit and tag that — the latter only validates while `main` has not
  advanced past the merge, because `changed_paths` is recomputed from `R..P`.
- Re-run `python scripts/check_release_manifest.py` after any change of tag target and
  attach the regenerated manifest, not an earlier copy.
- Write the annotated tag message as a release certificate, matching the shape of
  `git show --no-patch v1.0.0`: `R`, `P`, publication run, both digests, the evidence
  summary, the registered waivers, the carried limitations, and the external manifest
  sha256.
