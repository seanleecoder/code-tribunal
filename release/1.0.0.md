## Tagging

The external manifest binds `release_commit` and re-derives the `R..P` diff, so
the tag must point at a commit that satisfies it.

- **Do not squash-merge.** A squash rewrites `P` into a new commit and drops
  `0f86df6a6f698f44dd58f3007943786c0b90e528` from `main`'s history, which
  invalidates the manifest.
- **Do not tag the merge commit while the manifest names `P`.** If the release PR
  lands as a merge commit, `main`'s tip is a *new* commit and `P` becomes its
  parent. Either:
  - tag `v1.0.0` on `0f86df6a6f698f44dd58f3007943786c0b90e528` exactly; **or**
  - rebuild and re-validate the manifest against the merge commit and tag that:

    ```bash
    python scripts/build_release_manifest.py --tag v1.0.0 \
      --runtime-source 88bc9412b283d4a44328ab3ffd9f9708b0290f8e \
      --release-commit <merge-commit-sha> --out /tmp/release-manifest.json
    python scripts/check_release_manifest.py /tmp/release-manifest.json
    ```

    This is preferred when you want the tag on `main`'s tip. It only validates if
    `main` has not advanced past the merge, since `changed_paths` is recomputed
    from `R..P`.
- Re-run `python scripts/check_release_manifest.py` after any change of tag target
  and attach the regenerated manifest, not an earlier copy.

## Known limitations

### Known defect: GitHub pull requests that add or delete files

**On GitHub, findings can be silently dropped and the review can fail to complete
when the pull request adds or deletes a file.** This is a defect at this runtime
source, scheduled for 1.0.1.

- **Cause.** GitHub's prepared diff renders an added file with `--- /dev/null` (a
  deleted file with `+++ /dev/null`). The diff parser keeps that verbatim, and
  `context_hash_from_unified_diff` normalizes the parsed path while scanning for the
  anchor's file, which rejects `/dev/null` as an absolute path.
- **Effect.** Anchor finalization catches the error and drops that finding. When it
  affects every seat, each reviewer reports
  `raw_finding_count=N, accepted_finding_count=0, usable_for_resolution=false`,
  `consensus` exits 3, and `post`/`gate` are skipped — so the required `gate` check
  never succeeds and the pull request cannot merge.
- **When it triggers.** A finding on an added or deleted file always triggers it. A
  finding on an ordinary modified file also triggers it if an added or deleted file
  appears *earlier* in the diff, which is common because diff entries are ordered by
  path. If the added file sorts after every file with findings, the run is
  unaffected.
- **Scope.** GitHub only. GitLab is unaffected: its prepared diff emits
  `--- a/<path>` for added files rather than the sentinel. It affects real reviewers
  as well as the deterministic mock.
- **Not affected.** No state corruption and no crash: the error is contained by the
  existing `ValueError` handling, no malformed anchor is persisted, and
  cross-revision remap degrades to its content scan rather than failing.
- **Recognising it.** Look for `absolute paths are not allowed: /dev/null` in the
  reviewer job log, `dropped_finding_count` equal to `raw_finding_count` with
  `usable_for_resolution: false` in `out/status/<reviewer>.json`, and a `consensus`
  job exiting 3.
- **Workarounds.** Until 1.0.1: land file additions in a separate pull request from
  the changes you want reviewed, or re-run the review after the added file has
  merged. Disabling `merge_gate.enabled` unblocks merging but does not restore the
  lost findings.

### Other limitations

- **Trusted image pinning is not enforced inside the pipeline.** A consumer
  `.gitlab-ci.yml` can substitute the base/reviewer images by declaring them in
  its own top-level `variables:` and enabling variable forwarding; this was
  reproduced live (see the hostile-MR record). Containment relies on protected
  credentials being withheld from untrusted refs and on the operator-run
  `scripts/verify_pipeline_trust.py` auditor, which does reject such a
  composition. Run that auditor against your consumer config.
- **Credential isolation is evidenced narrowly**: protected credentials were
  withheld from a hostile MR on an unprotected ref in the hardened child
  topology. That is not a product-wide isolation guarantee. GitLab fork-based MRs
  are untested; GitHub external forks are skipped by design.
- A human `/ai-review wontfix` durably dismisses a finding and stops it
  re-posting, but does **not** clear the merge gate — consensus continues to
  report `block_merge`. Plan an operator escape hatch accordingly.
- A reviewer that omits the required `confidence` field has all of its findings
  dropped, which can silently degrade a panel. Observed with a weak default model.
- Network egress is not enforced at the container/runner boundary.
- Symlink-containing repositories are rejected during snapshot preparation.
- Cursor remains experimental, has no evidence row, and must not be described as
  evidence-backed.
- The deterministic mock (`AI_REVIEW_MOCK_SCENARIO`) cannot anchor a finding on a
  newly **added** file on GitHub, for the same root cause as the defect above, so
  evidence fixtures must modify an existing file.
