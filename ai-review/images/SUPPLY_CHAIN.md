# AI Review image supply-chain pins

The reviewer image keeps mutable package inputs in reviewed repository files:

- `package.json` and `package-lock.json` pin npm-distributed reviewer CLIs and npm integrity metadata. The builder prunes, in the same layer as `npm ci`, only content verified by that install: the platform packages that `claude.exe` and `opencode.exe` are hard-linked from, OpenCode's second x64 variant, and Codex's code-mode host (while `code_mode` stays off) and voice runtime.
- `cursor-agent.pin` records the Cursor CLI version, download URL, and SHA-256 because Cursor CLI is distributed outside npm. After the checksum passes, the `cursor-cli` stage deletes the package's macOS-only single-executable copies (`cursor-agent-sea`, `cursor-agent-worker-sea`), and fails the build if anything other than the darwin-gated signed-CLI chunk references them.
- `ripgrep.pin` records the ripgrep version, download URL, and two SHA-256 digests for the binary shipped to `/usr/local/bin/rg`: `sha256` for the release tarball and `binary_sha256` for the extracted `rg` itself, so what resolves on PATH is checked and not merely what was downloaded. OpenCode resolves `which("rg")` before downloading an unverified copy, so the pinned binary on PATH short-circuits the fetch entirely. `opencode_version` records the `opencode-ai` version this ripgrep belongs to, and the pin check enforces that equality.
- `python-constraints.txt` pins the direct and transitive Python packages installed into the base image.
- `base.Dockerfile` pins the Python base image by digest, and `reviewer.Dockerfile` uses the same digest as its standalone-build default.
- Every GitHub Actions workflow pins actions by full commit SHA with a comment naming the upstream tag, and every job container by digest. `make workflow-pins` runs zizmor's `unpinned-uses`, `unpinned-images` and `ref-version-mismatch` audits over them.

## Refresh process

[Renovate](../../renovate.json), installed as the hosted app, opens a pull request for each update to the npm CLIs, the Python pins, the base and builder image digests, and the action SHAs. It never touches the `ai-review-base` and `ai-review-reviewer` pins, which only a release commit changes (step 9), or the `.pin` files, whose checksums it cannot recompute (steps 5 and 6). A Renovate pull request is gated like any other: `make quality`, and the image workflow's `build-preflight` job, which builds both images and runs the probes in step 8. Review the upstream release notes before merging one.

1. Renovate updates the npm CLI versions in `package.json` and the lockfile together. To do it by hand, regenerate the lockfile from `ai-review/images` with `npm install --package-lock-only` under the pinned Node builder. The final image ships no Node runtime: `claude` and `opencode` link to their native executables, `codex` is an exec shim that sets the environment its `codex.js` launcher would, and the build fails if a pin moves any of them back to a JavaScript entry point.
2. Renovate updates each Python pin in `python-constraints.txt` and `requirements-dev.txt` together, one package at a time. It does not re-resolve the transitive set, so when an update moves a dependency's requirements, refresh the constraints from a clean resolver in the same pull request.
3. Renovate updates the base image tag and digest in `base.Dockerfile` and the `AI_REVIEW_BASE_IMAGE` default in `reviewer.Dockerfile` together, and `make supply-chain` fails if they differ. By hand, inspect the registry manifest, for example `docker buildx imagetools inspect python:3.14.8-slim-trixie`, and update both.
4. Renovate refreshes the Node builder and `debian:trixie-slim` digests in `reviewer.Dockerfile`; `make supply-chain` requires every `FROM` to stay digest-pinned. The builder tracks the stable Current line, not LTS.
5. Refresh `cursor-agent.pin` by selecting a versioned `downloads.cursor.com` artifact, recording its SHA-256, and rebuilding the reviewer image. If Cursor only exposes a moving installer for a release window, run the installer in a builder, hash the produced binary/archive, and document the weaker provenance in the pin-review commit. If the SEA pruning guard fails, re-read how the new launcher and `index.js` reach those files before you loosen or drop the guard.
6. Refresh `ripgrep.pin` whenever `opencode-ai` changes in `package.json`, including in a Renovate pull request; `make supply-chain` fails until you do, because the pin names the opencode version it belongs to. OpenCode resolves `which("rg")` first and otherwise downloads an unverified binary, so to learn the version the pinned opencode would fetch, run the pinned `opencode-ai` once where `rg` is absent from PATH and the cache is cold, then read the `ripgrep-<version>-<platform>` URL it requests (the binary it would drop into `$HOME/.cache/opencode/bin/rg`). Record that exact version and the new `opencode_version` in `ripgrep.pin`, together with **both** digests of the matching `x86_64-unknown-linux-musl.tar.gz` release asset — `sha256` of the tarball and `binary_sha256` of the `rg` extracted from it (`tar -xzf … --strip-components=1` then `sha256sum rg`). Then rebuild the reviewer image so the checksum, digest, resolution, and version guards re-run.
7. Renovate updates action SHAs and their tag comments, including in the canonical `ai-review/ci/review.github-actions.yml` and its installed copy in the same pull request. In CI, zizmor's `ref-version-mismatch` audit checks that each comment names the tag of its SHA.
8. Run `make supply-chain workflow-pins`, the repository test suite, and a local `docker build` of the reviewer image. The pinned artifacts are `x86_64`, so pass `--platform linux/amd64` on an arm64 host or the `ripgrep-bin` stage fails at its own `rg --version`. The `ripgrep-bin` stage and the final-stage runtime guard download, checksum, extract, resolve, digest, and version-check the pinned binaries — the steps static string checks cannot execute. After a reviewer-image build, run `scripts/smoke_opencode_search_tools.sh <reviewer-image>` (also a step in the publishing workflow's `build-preflight` job, so it gates merge on pull requests and publication on main) to prove that the `rg` on the OpenCode server's fixed PATH and the `opencode` the client launches are the pinned ones — each against a decoy earlier on the ambient PATH — that `rg` hashes to `binary_sha256` and reports the pinned version, and that the client's own generated config resolves `external_directory` to `deny` while `read`/`glob`/`grep` stay allowed. The probe runs with `--network none`, so a regression that restored the review-time ripgrep download cannot pass it.
9. After the trusted `main` publication succeeds, copy the source commit and both digests from the workflow summary. Update `.github/workflows/ai-review.yml`, `ai-review/ci/review.github-actions.yml`, and `ai-review/ci/review.gitlab-ci.yml` together; update `AI_REVIEW_TRUSTED_IMAGE_SHA` in the GitLab template to that same source commit. Digest changes remain reviewed rather than being committed automatically by the publishing workflow.
10. For every `cursor-agent.pin` bump, retry `--sandbox enabled` in the nested-container preflight; remove the allowlist exception if the new CLI can initialize its kernel sandbox there. The retry needs an authenticated CLI: without credentials, authentication stops the invocation before sandbox capability is established.

## Residual apt limits

The `cursor-cli` and `ripgrep-bin` builder stages in `reviewer.Dockerfile` carry deliberately parallel bodies (presence checks, placeholder rejection, pinned-URL download, checksum, extract) rather than sharing a base stage, so a change to one pinned artifact's verification cannot silently alter the other's. A shared verifying stage would be a fair refactor once a third pinned artifact appears; it is not worth putting the already-verified Cursor stage on a new base for two.

The base image installs Debian `ca-certificates` and `git` from the Trixie apt repositories without exact package-version pins. Apt repository snapshots would improve byte-for-byte rebuilds, but add mirror operations and security-update latency. The pinned base-image digest and Python/npm lock inputs keep the application-layer tools reproducible; apt drift is limited to explicit rebuilds after the base digest is intentionally refreshed.

## Cursor CLI egress exception

Cursor CLI cannot use OpenRouter or a custom base URL in agent mode. The default config keeps `reviewers.cursor.enabled: false`; when operators opt in, prompts, MR diffs, and readable repo-snapshot content are sent to Cursor's backend and billed through the Cursor account associated with `CURSOR_API_KEY`. The runner injects only the reviewer's declared credential and `adapters/cursor.sh` runs under `env -i`, so `OPENROUTER_API_KEY` is not forwarded to Cursor.

## Cursor sandbox exception

The pinned Cursor CLI's kernel sandbox is unavailable inside nested GitHub Actions job containers. The adapter therefore selects the CLI's native read-only Q&A mode on each print invocation with `--mode ask --sandbox disabled --trust`, avoiding a separate state-mutating setup command. Isolation for this reviewer depends on that mode, the sanitized disposable workspace, and `cli-config.json`, which allows `Read(**)` while denying relative writes with `Write(**)`, absolute writes with `Write(/**)`, and every shell command with `Shell(*)`. The repository tests verify that this policy is wired into every invocation. **Nothing verifies the pinned CLI's own runtime interpretation of those denies**, so a `cursor-agent.pin` bump could change it unnoticed. On GitHub the exposure is bounded rather than removed: the canonical workflow runs only when the pull request head is in the same repository and passes `CURSOR_API_KEY` only to the Cursor matrix entry, so this seat never processes fork-supplied content there. GitLab has no equivalent bound: a protected-ref pipeline started with pipeline variables can review a fork merge request ([security model](../../docs/SECURITY_MODEL.md#trusted-ci-delivery-and-reviewer-credentials)). Add a behavioural probe before relying on this seat for fork content. This is an explicit, weaker tradeoff rather than an equivalent replacement for kernel isolation.
