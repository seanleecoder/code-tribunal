# AI Review image supply-chain pins

The reviewer image keeps mutable package inputs in reviewed repository files:

- `package.json` and `package-lock.json` pin npm-distributed reviewer CLIs and npm integrity metadata.
- `cursor-agent.pin` records the Cursor CLI version, download URL, and SHA-256 because Cursor CLI is distributed outside npm.
- `ripgrep.pin` records the ripgrep version, download URL, and two SHA-256 digests for the binary shipped to `/usr/local/bin/rg`: `sha256` for the release tarball and `binary_sha256` for the extracted `rg` itself, so what resolves on PATH is checked and not merely what was downloaded. OpenCode resolves `which("rg")` before downloading an unverified copy, so the pinned binary on PATH short-circuits the fetch entirely. `opencode_version` records the `opencode-ai` version this ripgrep belongs to, and the pin check enforces that equality.
- `python-constraints.txt` pins the direct and transitive Python packages installed into the base image.
- `base.Dockerfile` pins the Python base image by digest, and `reviewer.Dockerfile` uses the same digest as its standalone-build default.
- `.github/workflows/publish-ai-review-images.yml` pins GitHub Actions by full commit SHA with comments naming the tracked upstream tag.

## Refresh process

1. Update npm CLI versions in `package.json` and regenerate the lockfile from `ai-review/images` with `npm install --package-lock-only`.
2. Update Python pins in `python-constraints.txt` from a clean resolver after reviewing upstream release notes.
3. Refresh the base image digest with a registry manifest inspection, for example `docker buildx imagetools inspect python:3.12-slim-bookworm`, and update both `base.Dockerfile` and the `AI_REVIEW_BASE_IMAGE` default in `reviewer.Dockerfile` to the same digest.
4. Refresh the pinned Node builder digest in `reviewer.Dockerfile` when intentionally changing the builder image.
5. Refresh `cursor-agent.pin` by selecting a versioned `downloads.cursor.com` artifact, recording its SHA-256, and rebuilding the reviewer image. If Cursor only exposes a moving installer for a release window, run the installer in a builder, hash the produced binary/archive, and document the weaker provenance in the pin-review commit.
6. Refresh `ripgrep.pin` whenever `opencode-ai` changes in `package.json`; `check_supply_chain_pins.py` fails until you do, because the pin names the opencode version it belongs to. OpenCode resolves `which("rg")` first and otherwise downloads an unverified binary, so to learn the version the pinned opencode would fetch, run the pinned `opencode-ai` once where `rg` is absent from PATH and the cache is cold, then read the `ripgrep-<version>-<platform>` URL it requests (the binary it would drop into `$HOME/.cache/opencode/bin/rg`). Record that exact version and the new `opencode_version` in `ripgrep.pin`, together with **both** digests of the matching `x86_64-unknown-linux-musl.tar.gz` release asset — `sha256` of the tarball and `binary_sha256` of the `rg` extracted from it (`tar -xzf … --strip-components=1` then `sha256sum rg`). Then rebuild the reviewer image so the checksum, digest, resolution, and version guards re-run.
7. Refresh action SHAs from the upstream action tag, keeping the adjacent comment with the human-readable tag.
8. Run `python scripts/check_supply_chain_pins.py`, the repository test suite, and a local `docker build` of the reviewer image. The pinned artifacts are `x86_64`, so pass `--platform linux/amd64` on an arm64 host or the `ripgrep-bin` stage fails at its own `rg --version`. The `ripgrep-bin` stage and the final-stage runtime guard download, checksum, extract, resolve, digest, and version-check the pinned binaries — the steps static string checks cannot execute. After a reviewer-image build, run `scripts/smoke_opencode_search_tools.sh <reviewer-image>` (also a step in the publishing workflow's `build-preflight` job, so it gates merge on pull requests and publication on main) to prove that the `rg` and `opencode` resolving on the adapter's fixed PATH are the pinned ones — each against a decoy earlier on the ambient PATH — that `rg` hashes to `binary_sha256` and reports the pinned version, and that the adapter's own generated config resolves `external_directory` to `deny` while `read`/`glob`/`grep` stay allowed. The probe runs with `--network none`, so a regression that restored the review-time ripgrep download cannot pass it.
9. After the trusted `main` publication succeeds, copy the source commit and both digests from the workflow summary. Update `.github/workflows/ai-review.yml`, `ai-review/ci/review.github-actions.yml`, and `ai-review/ci/review.gitlab-ci.yml` together; update `AI_REVIEW_TRUSTED_IMAGE_SHA` in the GitLab template to that same source commit. Digest changes remain reviewed rather than being committed automatically by the publishing workflow.
10. For every `cursor-agent.pin` bump, confirm that **Verify Cursor denies write and shell tools** passed for the published image before setting `AI_REVIEW_CURSOR_ENABLED=true`. Also retry `--sandbox enabled` in the nested-container preflight; remove the allowlist exception if the new CLI can initialize its kernel sandbox there.

## Residual apt limits

The `cursor-cli` and `ripgrep-bin` builder stages in `reviewer.Dockerfile` carry deliberately parallel bodies (presence checks, placeholder rejection, pinned-URL download, checksum, extract) rather than sharing a base stage, so a change to one pinned artifact's verification cannot silently alter the other's. A shared verifying stage would be a fair refactor once a third pinned artifact appears; it is not worth putting the already-verified Cursor stage on a new base for two.

The base image installs Debian `ca-certificates` and `git` from the Bookworm apt repositories without exact package-version pins. Apt repository snapshots would improve byte-for-byte rebuilds, but add mirror operations and security-update latency. The pinned base-image digest and Python/npm lock inputs keep the application-layer tools reproducible; apt drift is limited to explicit rebuilds after the base digest is intentionally refreshed.

## Cursor CLI egress exception

Cursor CLI cannot use OpenRouter or a custom base URL in agent mode. The default config keeps `reviewers.cursor.enabled: false`; when operators opt in, prompts, MR diffs, and readable repo-snapshot content are sent to Cursor's backend and billed through the Cursor account associated with `CURSOR_API_KEY`. The runner injects only the reviewer's declared credential and `adapters/cursor.sh` runs under `env -i`, so `OPENROUTER_API_KEY` is not forwarded to Cursor.

## Cursor sandbox exception

The pinned Cursor CLI's kernel sandbox is unavailable inside nested GitHub Actions job containers. The adapter therefore selects the CLI's native read-only Q&A mode on each print invocation with `--mode ask --sandbox disabled --trust`, avoiding a separate state-mutating setup command. Isolation for this reviewer depends on that mode, the sanitized disposable workspace, and `cli-config.json`, which allows `Read(**)` while denying relative writes with `Write(**)`, absolute writes with `Write(/**)`, and every shell command with `Shell(*)`. The repository tests verify that this policy is wired into every invocation, but only the trusted-main smoke can verify the pinned CLI's real interpretation of `Shell(*)`; keep that result as a hard enablement gate. This is an explicit, weaker tradeoff rather than an equivalent replacement for kernel isolation.

Before enabling Cursor from trusted `main`, `scripts/smoke_cursor_permissions.sh <reviewer-image> <cursor-model>` snapshots the workspace, then requires a successful real read probe to return an unpredictable per-run nonce without changing it. The hostile probe runs with a separate clean `HOME`, `TMPDIR`, and policy so read-phase state cannot weaken it. It then probes workspace creation and overwrite, redirected-home writes, and temporary-path shell effects. Cursor legitimately normalizes `cli-config.json` on startup by formatting it and adding runtime metadata, so the smoke re-parses the post-probe policy instead of requiring byte-for-byte stability: `Read(**)` must remain the only allow entry, all required write/shell denies must remain present, and `allow` plus `deny` must remain the only permission buckets. The smoke requires `python3` on the publisher host for this semantic validation. It distinguishes read-control failure, phase-specific filesystem or policy mutation, and hostile-probe execution failure while printing bounded diagnostic output. Cursor may also create its own runtime files under `HOME` and `TMPDIR`, so those directories are not hashed wholesale; the semantic policy, workspace, and explicit hostile targets are checked instead. Pull requests never receive `CURSOR_API_KEY` for this smoke. A publisher without that optional secret skips the check and must keep Cursor disabled. A publisher whose configured model is the discovery placeholder `auto` exits successfully with a warning; that expected discovery skip is not Cursor-enablement evidence. Pin the exact Composer slug in `review.yaml` and the publisher workflow together before a real-key smoke can run. This is a Cursor-enablement gate, not an image-publication gate. The two sequential probes can each run for up to 180 seconds. The smoke does not claim to prove network isolation; container-level egress remains the H2 limitation. Keep Cursor disabled for consumers until the trusted-main check passes.
