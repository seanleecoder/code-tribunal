# ADR-0002 — Post-1.0 review-output policy

- **Status:** Accepted
- **Date:** 2026-07-27
- **Decision:** SPEC-44/45/46 review-output policy

## Context

SPEC-44,
[SPEC-45](../improvement-specs/spec-45-critique-provenance.md), and
[SPEC-46](../improvement-specs/spec-46-unanchored-advisories.md) were drafted together as the
post-1.0 review-output sequence. Review of the first committed draft surfaced four questions that
are product policy rather than correctness, and that the specifications cannot settle by
themselves:

1. SPEC-44 makes every model-originated value render as literal data. Applied without a stated
   limit, that rule also covers closed enumerations, which changes the existing
   `**AI review: MAJOR correctness**` header for no safety gain — but exempting a field is only
   sound if the schema the renderer reads constrains it *and* something validates that schema
   before rendering.
2. SPEC-45 preserves critique reasoning that is currently discarded. Rendering all of it expanded
   costs real vertical space: on a panel of N reviewers a group has up to N−1 critics, and under
   SPEC-44 every rationale is a labelled fenced block.
3. SPEC-46 introduces non-line-anchored advisories. Advisory volume and quality have no
   after-the-fact suppression mechanism in this phase, because critique of advisories is
   deliberately deferred to its own specification.
4. SPEC-46 must decide what an invalid advisory `scope_paths` entry means — a broken advisory, or
   an over-claimed scope on an otherwise useful one.

These decisions are recorded here so the specifications can cite a decision source rather than
assert one, and so a later reviewer can distinguish an owner ruling from unreviewed drift.

## Decision

**1. The SPEC-44 rendering boundary is earned per field, and only where a validation boundary
enforces it.** Every free-text or path-shaped value renders through the literal API. A value may
render outside it only when the schema of the artifact the renderer reads closes its vocabulary
**and** the consuming stage validates against that schema. For inline and summary rendering that
artifact is `consensus.v1`, and both conditions currently fail: the schema enumerates
`final_severity` and `decision` but leaves `category` an unconstrained string, and the posting
stage never validates its input — `post.py`'s `cli` casts the loaded artifact without a runtime
check, unlike the consensus and gate stages.

Two changes therefore accompany the exemption: `consensus.schema.json`
`$defs.group.properties.category` is tightened to the `finding_batch.schema.json` category enum
(keeping `schema_version` at `consensus.v1`), and the posting stage validates the consensus
artifact against that schema before constructing a platform client. A schema test asserts each
exempt vocabulary is closed, and a zero-network regression asserts a schema-invalid artifact is
rejected before any posting API call. If either condition is ever removed, the exempt fields revert
to literal rendering.

**Scope of what validation buys.** Schema validation is a shape-and-vocabulary check, not an
authenticity or integrity check. It cannot detect a schema-valid but altered artifact, and it
establishes nothing about provenance. Its only job here is to make the exempt enums genuinely
closed at the point of use. Everything else stays safe because it renders through the literal API —
which is why the exemption is deliberately confined to closed enumerations rather than extended on
the strength of "the artifact is validated".

This also closes a pre-existing gap that is independent of the rendering question: an altered
consensus artifact — one that today's schema accepts, because `category` is an unconstrained
string — can place arbitrary text in the severity header, category, and consensus footer of a
posted review.

**2. Critique display is tiered; retention is not.** `critique_observations` records every
selected effective non-agree critique in full, unconditionally — the provenance obligation is
discharged by retention. Display is budgeted separately: a counts line is always visible,
disputes render their full rationale, noise on a surviving group is elided to one line, and
valid-duplicate rationale is retained in the artifact but not rendered. `Found by` appears on
summary entries only, because the inline consensus footer already emits the same sorted
`contributing_reviewers`.

**3. The majority-noise disposition audit is opt-in.** It is written to the consensus artifact and
the review job output by default. Posting it to the merge-request summary requires
`critique.show_disposition_audit: true` (YAML-only, default `false`). Suppression exists to reduce
maintainer clutter, and the audit's audience is whoever tunes the panel.

**4. `reviewers.<name>.max_advisories` defaults to 3, not 10.** The range remains 0–10. With
advisory critique deferred, this cap and the required `anchor_attempt_reason` are the only
mechanical controls on advisory volume and quality in this phase. A default of 10 across the four
shipped reviewers would permit 40 non-gating entries in one summary comment, and advisories
consume neither `max_posted_surface_findings` nor `max_fyi_findings`. No merge-request-level cap is
added; the per-reviewer default is what bounds the total.

**5. Invalid advisory `scope_paths` is handled by failure mode.** A malformed, absolute, or
traversal-shaped path — or an unavailable diff — drops the whole advisory, because output that
cannot express a well-formed repository path is evidence about the advisory as a whole. A
well-formed relative path that is merely absent from the changed set degrades the entire scope to
canonical `[]` (MR-wide) and keeps the advisory, because citing a relevant unchanged consumer file
is a common benign case and `scope_paths` is display-only — never dereferenced, never used to
anchor or match. Neither case ever keeps a partial list.

## Consequences

- Default critique visibility is lower than the first draft proposed, and the tiers differ by
  verdict. In the merge request, a counts line is always visible; expanding the disclosure shows
  **full dispute rationale** but only an **elided one-line** noise rationale. Full noise text and
  all valid-duplicate rationale are reachable only in the consensus artifact and job output.
  Nothing is lost from the artifact, but not everything retained is reachable from the UI.
- Majority-noise groups are invisible in the merge request unless an operator opts in. Panel
  tuning uses the artifact and job output.
- The advisory budget is deliberately conservative. Decisions 2–4 are revisitable once critique of
  advisories has its own specification, since peer verdicts would then provide the missing
  suppression mechanism.
- `consensus.v1` accepts a narrower `category` input than before. Every artifact the pipeline has
  produced satisfies the tightened enum, because `category` has always been copied from a
  schema-validated finding; a hand-edited or third-party artifact with an arbitrary category now
  fails validation, which is the intended effect.
- The posting stage now rejects a **schema-invalid** consensus artifact instead of rendering it. An
  operator replaying a hand-edited artifact that previously posted will see a validation error if
  the edit broke the schema; that is intended, and it makes the three consensus-consuming stages
  behave identically.
- A schema-valid alteration still posts. Validation is not an integrity control, and the literal
  renderer only guarantees that such content **cannot inject Markdown, markers, or layout** — it
  says nothing about semantics. A schema-valid altered `summary.block_merge` still decides the
  merge gate in `gate.py`, and an altered `decision` still moves a finding between inline, summary,
  and dropped. Consensus-artifact integrity between pipeline stages is **not addressed by this
  decision** and remains an open question; nothing here should be read as mitigating it.
- The `**AI review: <SEVERITY> <category>**` header is preserved unchanged.

- SPEC-44 and SPEC-46 are re-estimated from **M to L**. This is a consequence of the decisions
  above and of the defect fixes recorded alongside them, not a separate judgment: decision 1 adds a
  schema tightening and a posting-stage validation to SPEC-44, and decisions 4–5 add a required
  field, a degrade counter, and split scope handling to SPEC-46. Each specification's "Deviations
  from the original draft" section itemizes what drove its estimate. SPEC-45 remains **M**.

All three specifications remain **Proposed (post-1.0)**. This decision record fixes the intended
policy; it does not mark any of them as shipped.
